Catching an Intruder Three Ways

Multi-Source Detection & Forensic Reconstruction of a Simulated Windows 11 Intrusion Using Open-Source Tooling

  • Endpoint Logs

One attack, three independent lenses — and no single source saw all of it.

01 Overview

The research question

Incident responders rarely get the whole story. They reconstruct an attack from fragments: an event log here, a prefetch file there, maybe a memory image if they were quick. Every source is incomplete in its own way. We wanted to measure how incomplete, by running a known attack and checking what each lens could recover.

When a known set of attacker techniques is executed, how much can be detected and forensically reconstructed from each evidence source — and where does each one succeed or fail?

  • 11ATT&CK techniques attempted
  • 7ran with full success
  • 8/8executed techniques detected
  • 297/297evidence files hash-verified

02 Methodology & Safety

A five-step pipeline

  1. 1

    Isolate

    Windows 11 25H2 VM on VMware, host-only networking.

  2. 2

    Instrument

    Sysmon + PowerShell script-block logging.

  3. 3

    Attack

    11 ATT&CK techniques via Atomic Red Team.

  4. 4

    Acquire

    Memory, logs, prefetch, registry, all SHA-256 hashed.

  5. 5

    Analyse ×3

    Detection, Disk and Memory tracks, run independently.

Safety

Contained by design

All attacks ran only against our own VM on host-only networking with no route to any real network, verified by 100% packet loss. No external or institutional system was ever touched.

06 Results

Three tracks

Track 1 · Detection over logs

  • 10,277events processed by Hayabusa
  • 5,608rule hits (~50% data reduction)
  • 8/8executed techniques detected
  • 2custom Sigma rules written

Hayabusa ran the Sigma corpus offline over the Sysmon and PowerShell logs. Chainsaw independently confirmed the results. All 8 executed techniques fired at least one rule. Two of them came with caveats:

  • T1057 missed by default rules. The tasklist discovery wasn't flagged by the stock corpus. We only caught it with threat-hunting and a custom Sigma rule.
  • T1112 mis-tagged as T1137. The detection fired, but under the wrong ATT&CK ID. A defender triaging by ID would attribute it to the wrong technique.

Track 2 · Disk artifacts

  • 0–4 sprefetch offset from ground truth
  • 7 dayspersistence still live afterwards
  • 0WMIC.EXE prefetch entries
  • Prefetch timed every technique. It placed each technique's binaries within 0–4 seconds of ground truth. arp, netsh, nbtstat, systeminfo and tasklist each ran exactly once, so those runs can only be the attack.
  • Negative evidence. There is no WMIC.EXE prefetch at all. The absence independently confirms that the WMI techniques failed.
  • Persistence outlived the attack. Seven days later, an HKCU Run value named Atomic Red Team and two scheduled tasks (OnLogon / OnStartup, action cmd.exe /c calc.exe) were all still live.
  • T1112 left no registry trace. It rewrote a value to its existing default, so only Prefetch can prove it ran.

Track 3 · Physical memory

Documented limitation

Memory acquisition failed on a hardened OS

  1. Acquire WinPMEM's kernel driver would not load on hardened Windows 11 25H2 error 0x241.
  2. Fallback Captured memory by suspending the VMware hypervisor instead.
  3. Parse Volatility 3 could not build a translation layer from that image, on two different machines.
  4. Sweep A raw string sweep of the 1.9 GB image returned 0 attack indicators.

Takeaway: on a current hardened OS, acquire memory promptly with a validated tool, and verify the image before the system changes.

07 Errors We Solved

What broke, and what we did

  • ProblemHyper-V blocked VirtualBox

    FixSwitched to VMware Workstation.

  • ProblemWindows 11 refused to install (4 GB RAM / 52 GB disk minimums)

    FixResized the VM to 4 GB / 60 GB.

  • ProblemDefender blocked our PowerShell (Tamper Protection, 0xc0000142)

    FixDisabled real-time protection and added an exclusion via the Security GUI.

  • ProblemWindows updated mid-setup

    FixRe-verified timezone, Sysmon and Defender state before attacking.

  • ProblemWinPMEM driver blocked (0x241)

    FixFell back to a VMware suspend image and documented it.

  • ProblemVolatility couldn't parse the suspend image

    FixReported it as a modern-OS acquisition finding.

Who did what, and what we learned

  • Mansi Sharma

  1. No single source is complete.
  2. A detection that fires is not necessarily a correct detection.
  3. Persistence lives on disk long after an attack; memory is fleeting.
  4. On a hardened OS, acquisition is the hard part.
  5. Upfront instrumentation decides what evidence exists at all.
  6. Documenting failures honestly makes the work stronger.

Limitations

  • Single isolated host
  • Small, discovery-heavy technique set
  • Evidence collected one week after the attack
  • Results depend on the rule corpus

Future work

  • Add a second host for network forensics & lateral movement
  • Capture memory promptly with a validated acquirer
  • Expand techniques & custom detections
  • Publish Vagrant/Ansible automation
